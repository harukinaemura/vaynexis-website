OpenAI APIのZero Data Retentionだけで十分？機能ごとに残るデータの確かめ方

要点

API に送ったデータは、明示的にオプトインしない限り OpenAI のモデルの学習には使われないとされています。ただし、残るデータは［Abuse monitoring logs］（不正利用の監視ログ）と［Application state］（機能の動作のために残るデータ）の2種類に分けて説明されています。 Zero Data Retention は監視ログからお客様の内容を外す管理で、OpenAI の事前の承認が条件です。有効にしても、表で対象外とされた機能は Application state を保存することがあります。

公開：2026年11月18日／情報の確認日：2026年11月17日（出典はこの記事の最後）

OpenAI API を使う社内ツールの見積もりで「学習には使われません」と説明されても、ファイルや検索用のデータがどこに何日残るかは、機能の名前ごとに別に確かめる必要があります。

公式ページ・公式ヘルプなどの一次資料を2026年11月17日に確かめました。機能や制度は変わることがあるので、使う前に各ページで最新の状態を確認してください。法律・税務・労務の判断や、効果を約束するものではありません。

例は説明のための架空の例です。確認表や記録項目は当社の整理です。公式機関が示す様式ではありません。

  2. 2つの管理の違いと、選ぶ人
  3. 機能の名前で表を引く
  4. 対象の機能でも残る場面
  5. 委託先に聞く項目（架空の例）
  6. 確認表

1．「学習しない」と「残らない」を分けて聞く

確認日：2026年11月17日。

対象は、OpenAI の API を自社の仕組みに組み込む場合で、ChatGPT のアプリの設定は扱いません。

「API なら学習に使われない」という説明だけで、見積書や問い合わせ文を流してよいと決めると、どこに何日残るかの確認が抜けます。監視ログは、プロンプトや応答などの内容を含むことがあり、既定では API のすべての利用で作られ、最大30日保持されるとされています（法律で長い保持が必要な場合などを除く）。 もう一方の Application state は、一部の機能が、頼まれた処理を果たすために残すデータです。こちらは機能ごとに条件が違うため、後の表で引きます。

社内の決まりとしては、「学習に使われるか」「監視ログに何日残るか」「機能の動作のために何が残るか」の3つを分けて、送ってよい情報の範囲を決めます。

2．2つの管理の違いと、選ぶ人

ページには、Modified Abuse Monitoring と Zero Data Retention の2つが並んでいます。Modified Abuse Monitoring は、まれな場合の画像とファイルの入力を除いて、すべてのエンドポイントで監視ログからお客様の内容を外し、プラットフォームの機能はすべて使える、と説明されています。Zero Data Retention は、監視ログから外す点は同じで、加えて一部のエンドポイントの動きを変えます。 会話の履歴を OpenAI 側に残して使う作りかどうかで向き不向きが変わるため、選ぶ前に、作る仕組みが何を OpenAI 側に残す前提かを開発した人に確かめます。

どちらも OpenAI の事前の承認と追加の要件の受け入れが必要で、承認後は API の組織またはプロジェクトの単位で選べます。承認されると［Settings → Organization → Data controls］に［Data Retention］のタブが表示され、プロジェクトごとに［default］で組織の設定を引き継ぐか、明示的に選ぶか、［None］で外すかを決めます。

料金や契約の条件はこのページには書かれていません。申し込む前に窓口の回答を文書で受け取り、条件は変わりうる前提で控えを残します。組織で Zero Data Retention を選んでいても、社内ツールの API キーがあるプロジェクトが［None］なら意図した状態になりません。設定を変えられる人を決め、変えたら日付と理由を記録します。

また、これらを有効にした顧客は、自社の利用者が OpenAI の方針に従うことと、適用される法律の上での報告などの要件を守ることに責任を負うとされています。 監視ログから内容が外れる分、社員がどう使うかの決まりは会社の側で持つことになります。

3．機能の名前で表を引く

ページには、エンドポイント（機能の入口）ごとの保存の条件が表で示されています。事務の仕組みで出てきそうなものを抜き出します。

エンドポイント監視ログApplication stateZDRの対象
/v1/responses30 daysNone（例外あり）Yes（制限あり）
/v1/embeddings30 daysNoneYes
/v1/audio/transcriptionsNoneNoneYes
/v1/files30 daysUntil deleted*No
/v1/vector_stores30 daysUntil deletedNo
/v1/batches30 daysUntil deletedNo

読み方の要点は2つです。1つ目は、文字起こしの /v1/audio/transcriptions のように監視ログの保持そのものが None とされている機能もあれば、多くの機能は30日とされていること。2つ目は、ファイルを上げる /v1/files、検索用に文書をためる /v1/vector_stores、まとめて処理する /v1/batches は、Application state が削除されるまで残り、Zero Data Retention の対象外とされていることです。 社内の規程集を上げて検索させる作りなら、これらを使っていないかを、作った人に機能の名前で確かめ、使うなら消す時期と担当を決めておきます。

4．対象の機能でも残る場面

  • Responses API は既定で Application state を少なくとも30日保持しますが、組織で Zero Data Retention を有効にすると、［store］は true を指定しても常に false として扱われます。
  • バックグラウンドのモードでは、ポーリングのために応答のデータをおよそ10分ディスクに保存すると書かれています。Prompt caching で GPU のローカルの記憶域に置かれるデータは、24時間の期限の後は保持されないとされています。
  • 画像やファイルの入力は受け付けたときに CSAM の検査がされ、疑いが検出されると Zero Data Retention でも人による確認のために保持されます。remote MCP server へ送ったデータは、その第三者の保持の方針に従います。
  • Assistants API に関わるデータは削除してから30日後に消され、削除しないものは無期限に保持されます。ファイルは手動で削除するか、［expires_after］で自動で消す設定ができます。

承認を受けた顧客でも、書面で事前に知らせたうえで、特定のモデルを Zero Data Retention の対象から外すことがあると書かれています。 通知を受け取る担当を決め、届いたら使うモデルと設定を見直します。
