PR TIMESで自社の配信先にプレスリリースが届かないときの確認先と記録

要点

自社の配信先に届かないときは、広報担当が送信元・対象の配信先・操作した内容をそろえ、設定担当に認証の状態を確認し、解決しなければ配信サービスの窓口へ引き継ぐ流れにします。配信前に操作が止まった状態と、送信後に届かない状態を記録で分けることが出発点です。

公開：2026年11月4日／情報の確認日：2026年11月4日（出典はこの記事の最後）

この記事は、PR TIMESのインポートリストで自社の配信先にプレスリリースが届かない小さな会社の広報・事務担当者が、だれに何を確認し、何を記録して引き継ぐかを整理するためのものです。

公式ページ・公式ヘルプなどの一次資料を2026年11月4日に確かめました。機能や制度は変わることがあるので、使う前に各ページで最新の状態を確認してください。法律・税務・労務の判断や、効果を約束するものではありません。

例は説明のための架空の例です。確認表や作例は、当社の考えをまとめたもので、公式の機関が示しているものではありません。

  1. まず、送る操作のどこまで進んだかを確かめる
  2. 送信元の認証は設定担当に引き継ぐ
  3. 問い合わせには事実と依頼先をそろえる
  4. 配信停止は、設定変更と分けて確認する
  5. AIには確認依頼の下書きまでを任せる
  6. 確認表
  7. 自社の事務の手順まで形にしたいとき

1．まず、送る操作のどこまで進んだかを確かめる

確認日：2026-11-03

広報担当が、自社で用意した報道関係者の連絡先へ発表文を送ろうとし、配信先を選ぶ段階で止まった場面を考えます。「届かない」とだけ記録するより、どの画面で何が起きたかを残すと、確認を依頼する相手が状況を追いやすくなります。

PR TIMESのインポートリストでは、送信者名と送信元メールアドレスに自社の情報を設定できます。 配信済みのプレスリリースに設定したメディアリストは、管理画面の「プレスリリース」から「プレスリリース一覧」で確認できます。

広報担当は、対象の送付先一覧、使った送信元、選択した配信方法、操作後の表示を手元の記録と照合します。送る操作を終えていない状態と、送ったつもりの状態を分け、表示された文言も省略せずに控える進め方です。本文の書き直しに着手する前に、送付の準備と操作を見直します。

2．送信元の認証は設定担当に引き継ぐ

過去の公式案内では、送信ドメイン認証の設定開始から完了までに、利用企業と提供元のそれぞれに工程があると案内されています。 過去の案内は仕組みを理解する参考にし、配信の可否や操作は、現行の公式ヘルプと利用中の画面で照合する扱いにします。

現在の公式ヘルプでは、インポートリストの送信元アドレスで認証が未設定の場合、そのリストは配信先に選択できないと案内されています。 設定に進む際は、「設定＞送信ドメイン認証」の画面にある情報をシステム担当者に渡すよう案内されています。

既にSPFを設定している場合について、公式ヘルプは既存のレコードへの追加を案内しています。 広報担当が設定値を推測して書き換えるのではなく、既存の設定を管理する社内担当者や委託先に、利用中の画面と公式案内を渡す進め方がよいです。担当者には「対応した」という返答だけでなく、対象の送信元、確認した画面、変更の有無、確認後の状態も記録してもらいます。

以前の完了連絡が手元にあっても、今回使う送信元と一致するかを照合することが大切です。別の発信業務の設定まで自己判断で変更せず、担当者が確認した範囲を広報側にも残します。

3．問い合わせには事実と依頼先をそろえる

確認依頼は、原因の推測よりも、観察した事実から書くとよいです。対象の発表文と送付先を特定できる記録をそろえ、誰が何を調べ、何がまだ分からないかを残します。

残すこと確認を依頼する相手引き継ぐ内容
対象の発表文と送付先広報担当題名、送付先一覧、配信したつもりの対象
操作した内容広報担当選んだ配信方法、操作の段階、画面に出た文言
使用した送信元社内の設定担当・委託先利用中の画面にある情報、過去の対応記録、今回の確認結果
解消しない状態配信サービスの窓口対象を特定する情報、症状、社内で確認済みの範囲
受信側から得られた情報広報担当が窓口となって受信側へ届かなかった対象と、相手が確認できた事実

表は、問い合わせを準備するための整理です。原因を判定する表ではありません。受信側に確認を依頼する際も、認証の失敗や配信停止と決めず、相手が把握している事実をそのまま戻してもらう形にします。

依頼後は、返答を受けた人だけの手元に残さず、調べた範囲と残る確認先を同じ記録に追記します。窓口への問い合わせには、社内で確認したことを添えると、同じ質問の往復を整理しやすくなります。

4．配信停止は、設定変更と分けて確認する

受信者がワンクリック解除を行うと、次回のプレスリリースから配信が停止されます。 配信停止の解除による再開は、プレスリリースの受信者からの依頼でのみ可能です。

相手から配信停止の意思が示されている場合は、送信元を変えたり別の一覧に入れ直したりして送り続ける対応を避け、社内で扱いを共有する進め方にします。不達の調査と、受信者の希望を受け止める対応を分けて記録するとよいです。

公式ヘルプセンターには、FAQで解決しない場合のカスタマーサポート＆サクセスデスクへの問い合わせ案内があります。 問い合わせ時は、配信先を選べないのか、操作を終えた後の不達なのかを明記し、社内の確認結果と合わせて伝えます。認証の調整だけで届くと判断せず、窓口から追加で求められた確認事項を担当者へ戻す流れです。

5．AIには確認依頼の下書きまでを任せる

AIを使う場合は、広報担当がまとめた記録から、社内向けの確認依頼や窓口向けの問い合わせ文の下書きを作る用途にとどめます。観察していない原因を補わせず、分かっていることと、相手に尋ねることを分ける使い方です。

渡す材料は社内で利用を認めた範囲に絞り、認証情報や送付先の連絡先一覧をそのまま貼り付ける運用は避けます。設定を書き換える内容や再送の判断を下書きだけで確定せず、人が記録と照合してから依頼します。

指示文では、次のように作業の範囲を区切ります。

目的：プレスリリースの配信について、担当者への確認依頼の下書きを作る。
材料：社内で共有を認めた操作記録と、確認済みの返答。
記録にある事実だけを使い、原因を推測して書き足さない。
確認済みのこと、未確認のこと、相手への質問を分ける。
不足する情報は質問として残す。
設定値の生成、元の記録の変更、送信や再送は行わない。

下書きを読む際は、記録にない原因が断定されていないか、返答の内容が広げられていないかを確認します。設定担当からの返答と窓口への依頼内容がつながっていれば、次に誰が何を確認するかが見えやすくなります。

6．確認表

公開・共有の前に、この表で確かめます。

確認確かめること
□対象の発表文、送付先、使用した送信元を特定したか
□配信前に止まった状態と、送信後に届かない状態を区別したか
□操作した内容と表示された文言を記録したか
□設定担当に確認を依頼し、対象と結果を記録したか
□受信者による配信停止を、設定の問題と分けて確認したか
□窓口へ確認済みの範囲を伝え、残る確認先を共有したか
□AIの下書きに、記録にない原因や未承認の対応が入っていないか確認したか

ここまでの確認を、自社の事務の手順書や、AIの結果を確かめる検査まで形にしたい場合は、当社のように、手順と検査の設計まで行う相談先が選択肢になります。オンラインは全国から対応しています。

自社の事務のどこから確認を入れるかを相談したい場合は、初回無料相談をご利用ください。法律・税務・労務の判断や、効果の約束は行いません。
